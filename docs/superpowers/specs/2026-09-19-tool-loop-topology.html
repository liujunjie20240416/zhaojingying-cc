工具循环拓扑

在现有四个 Agent 节点之外，新增 两个 ToolNode 节点与 四条边，让 Memory Agent 与 Conversation Agent 各自获得「模型自主决定调什么工具、调几轮」的能力。图中橙色部分为本次新增，其余节点与边保持不变。

图结构

相对现状的改动

  • 01新增 2 个 ToolNode 节点与 4 条边（图中橙色）。原有四个节点、memory_done / emotion_done 防环不变量均不动。
  • 02route_after_memory 从二选一（emotion / conversation）变成三选一，多出 memory_tools 分支；conversation → END 从固定边变成条件边，判据是 tool_calls 是否为空。
  • 03state 新增 tool_steps 计数（每回合重置，两个循环各自计数），步数用尽时条件边强制走出口，丢弃剩余 tool_calls 而不报错。
  • 04检索逻辑本身一行不重写：七个工具内部全部复用既有实现（ConversationHistorySearch、search_semantic、TimeChunk / TopicTag 查询、QueryRewriter.plan）。

证据链怎么不断。工具返回给模型看的是简短文本（带 [msg_index] 编号），同时把结构化证据写进 ToolMessage.artifact，由包装层收集回 state 并汇入 reply_provenance。模型上下文不被长 JSON 污染，retrieved_raw 的溯源能力保持不变。

给建议顺序，但不强制。Memory Agent 的系统提示保留现有最佳实践（先定时间段 → 再查原文 → 不够再查话题），同时明确告诉模型可以跳过或换序。保住了现有质量下限，控制权仍然交了出去。

循环安全边界

项策略
步数memory ≤3 步、conversation ≤2 步；超限丢弃 tool_calls 用已有内容继续，不报错
单次工具超时15s（检索全为本地 SQLite / LanceDB，正常百毫秒级；LLM rerank 内部已有降级）
累计预算循环内工具累计 >30s → 强制结束循环，用已有证据继续生成
工具异常返回 ToolMessage 错误描述交给模型自行决策（重试 / 换工具 / 放弃），不抛断整图
全工具失败回落到现有降级路径：有界原文投影 / 空记忆上下文继续生成
并发与写入工具全部只读，不进写入链路；写入仍走原有 Reflection 与导入的事务边界
